# Ross AI Assessment MVP

AI-assisted software engineering risk assessment MVP for Ross Video, integrating literature-based concepts, KNIME analysis, and activity evaluation.

A React + Vite + Tailwind browser proof of concept for the master's capstone **Risk-Based Assessment of AI-Assisted Software Engineering Activities**. The application supports a repeatable human assessment; it does not make autonomous AI judgements.

## Start locally

Install Node.js 22 LTS or newer. In a terminal in this repository, run:

```sh
npm ci
npm run dev
```

Open the Local URL printed by Vite. Stop the server with Ctrl+C.

```sh
npm test        # unit checks for evidence rules, import validation, and persistence
npm run build  # production output in dist/
npm run preview
```

For desktop and mobile interaction tests:

```sh
npx playwright install chromium
npm run test:e2e
```

Tests use system Chromium if present, otherwise Playwright's browser. Set `PLAYWRIGHT_CHROMIUM_PATH` to select another Chromium binary. Browser fixtures are synthetic, not research evidence.

## What works

- **Dashboard:** all active groupings are visible by name with their questions, factors, concept mappings, and direct edit/assess links. Activity counts and evidence completeness come from the browser workspace.
- **Activity profiles:** A1 bug fixing, A2 agent-supported development/build-and-test, A3 code review; create, search, edit, and delete additional profiles. Record scope, owner, tool, and supporting files.
- **Assessment rubric:** editable factors within a variable set of explicitly provisional groupings, human-selected statuses, written rationale, source links, evidence links, and unresolved conditions. Partial requires a condition. Changed factors or evidence require reapplication without rewriting the earlier human status.
- **Recommendation map:** one visible follow-up rule per active factor, category filters, linked literature concepts, recorded evidence, and unresolved conditions. Each rule explains its inputs and logic, including reapplication conditions.
- **Method & concepts:** add, edit, archive, or restore groupings; add, edit, move, archive, or restore factors/questions/controls; create, edit, archive, and map literature concepts; inspect source records and local method history. The manual Excel → KNIME → GitHub workflow remains documented.
- **Portability:** browser-local saving; JSON export includes the entire editable method, concept library/mappings, evidence notes, and file bytes. Validated restore asks before replacing current records. Original v0.1 browser data and backups migrate without dropping evidence.
- **Human review:** a named reviewer can mark an activity reviewed after all active factors across the active groupings have current recorded assessments. Evidence need not all be Present. Editing a profile, file collection, or assessment clears the previous checkpoint.

No MCP, external AI API, authentication, server, or remote database is included. Uploaded files are never automatically analyzed or sent to an AI service.

## Edit the method and evidence from the website

1. **Dashboard:** the current draft groupings are visible. Select **Edit grouping**, or open **Method & concepts → Groupings & factors**.
2. **Groupings:** use the pencil icon to rename a grouping or edit its description. Use **Add grouping** for a new area, **Archive grouping** to retire one, and **Show archived groupings → Restore grouping** to bring one back. Existing IDs and evidence are retained; restored grouping factors require reassessment.
3. **Factors/questions/controls:** select **Add factor**, or edit a factor's name, grouping, question, recommendation, guidance, and literature links. The method supports up to 120 factors, including archived definitions. Archive and restore keep existing assessment history instead of deleting it.
4. **Literature:** open **Concept library → Add concept**. Enter an actual ID, definition, citation, and explicit grouping mappings. Existing IDs remain stable. Concepts can be edited, archived, or restored. No research records are generated by the app.
5. **Evidence:** select an activity, attach a file or add written evidence, then use its pencil icon to edit its title/description, note content, or replace a file. Image previews are supporting material only.
6. **Reapplication:** updated factor criteria, linked concepts, or linked evidence preserve earlier judgements and flag them for reassessment. Earlier criterion/source snapshots recorded by this version are available in the rubric. Record the human assessment again to clear that factor's reapplication flag. Re-recording deliberately replaces the current record; export a backup first to keep a complete earlier workspace.
7. **Backup/share:** **Export JSON** includes local method definitions, history, concept mappings, assessments, notes, and files. **Restore JSON** imports them into another browser after confirmation.

All editor changes apply to **this browser workspace**. They do not update every visitor, GitHub, or the tracked `data/concepts.json`. Publishing approved method content globally is a separate reviewed source update; no shared database has been introduced.

## Method status

The existing `data/concepts.json` contains **`{"concepts": []}`**. It is connected and retained unchanged. The project owner will provide the finalized literature concepts and their mapping later. The original target of 15 concepts and six groupings describes the initial research structure; neither count is a permanent method constraint. Per that instruction, the six working grouping labels and recommendation prompts remain visibly **provisional**, and no concepts, references, or source mappings have been invented.

`0.2-draft` identifies the browser implementation, not a validated research release. The UI distinguishes implemented features from planned pipeline automation and future collaboration.

Evidence statuses are **Present**, **Partial**, and **Not Evidenced**. They express evidence availability, not risk severity. Starter entries default to Not Evidenced with `recorded: false`; they are distinguished from a human-recorded assessment. Recording any status requires written evidence or rationale.

Evidence coverage = active factor records with current Present evidence ÷ total active factor records. An open condition exists when a factor has no current assessment, a non-Present status, or a non-empty unresolved condition. Records needing reapplication are shown separately from Not Evidenced. These are transparent follow-up prompts, not risk scores, deployment approval, or safety certification. Reviewed is an explicit human workflow checkpoint and can coexist with unresolved conditions.

## Concept source and KNIME

The Vite plugin in `vite.config.js` serves the existing root `data/concepts.json` in development and copies its bytes unchanged to `dist/data/concepts.json` during build. It never rewrites the source or the `knime/` folder. Both existing source directories are preserved.

The confirmed source envelope is an object containing a `concepts` array. Because the array is empty, individual entry fields are not yet established. The conservative adapter in `src/lib/concepts.js` supports the following candidate fields for future reviewed records and local inspection:

| Display field   | Supported source fields                                    |
| --------------- | ---------------------------------------------------------- |
| ID              | `id`, `code` (otherwise an explicit source row identifier) |
| Title           | `name`, `title`, `concept` (required for each entry)       |
| Description     | `description`, `definition`                                |
| Source grouping | `grouping`, `group`, `category`                            |
| Reference       | `source`, `reference`, `citation`                          |

It also accepts a plain array for optional local imports. Unsupported structures produce a visible error. Raw source fields are retained for inspection. Mappings are human-entered via `groupingIds`, an array of stable grouping IDs. Source grouping labels are preserved but never converted into an assessment mapping automatically. Local concept imports are browser overrides, included in exports; “Use repository source” returns to the tracked file.

The retained `knime/ross-literature-analysis.knwf` archive contains CSV readers/writers, text processing, term weighting, and clustering nodes. **It is not a verified JSON-export pipeline.** The documented process includes human review and manual preparation of the concepts JSON from reviewed output. KNIME execution and automated Excel/CSV/JSON conversion are not implemented. See [method updates](docs/METHOD-UPDATES.md).

## Local storage and supporting files

Records and file bytes are kept in this browser's `localStorage`, per origin. Another browser, device, or deployment URL has a separate workspace. Clearing browser data removes it; export a backup before clearing data or changing origins. Browser storage has no encryption or access control. Use only non-confidential demonstration material.

Files are limited to 1 MB each and 2.5 MB across the workspace. Each activity supports up to 100 evidence records (files or written notes). Notes are subject to browser storage capacity but do not use the file-size allowance. File names/descriptions and note text can be edited; files can be replaced, and safe image formats can be previewed. A linked file must be unlinked from rubric records before removal. Downloads use binary blobs; active document types are not embedded or executed by the app.

Save failures are displayed and leave changes in memory for export. Unreadable original storage is preserved and can be exported for recovery; new changes stay in memory until a supported backup is restored. Restore checks schema/method versions, IDs/codes, evidence references, attachment sizes, statuses, rationale, and review checkpoints. Schema 1 / method 0.1-draft backups migrate automatically to schema 2 / method 0.2-draft, preserving original factor IDs, statuses, rationale, and evidence bytes. Other versions are rejected for explicit migration review.

**Exports include attached evidence. Keep assessment exports and confidential artifacts out of repository commits.** Environment files, backups using the app's default filenames, build output, dependencies, and test recordings are ignored.

## Netlify setup

After reviewing the pull request, connect this repository to Netlify:

- Build command: `npm run build`
- Publish directory: `dist`
- Node.js version: 22
- No environment variables or paid backend services are needed.

`netlify.toml` sets these options and security headers. Hash routes such as `/#/rubric` work with static hosting and page refreshes without redirect rules. The concept source is a public static asset in the build, so review its content before publishing.

No deployment is created by this change. A Netlify deploy preview can be configured for review before merging.

## Client demonstration

Use the [client walkthrough](docs/CLIENT-DEMO.md) for a 4–5 minute presentation of one synthetic A1 bug-fixing example. The story is activity context → supporting evidence → human judgement → transparent follow-up → reapplication. Method configuration is an optional follow-up topic.

## Adapt the method as research evolves

The six provisional starter groupings can grow or shrink. The dashboard, rubric, evidence-completeness denominator, and recommendations follow active method definitions. Browser limits are 100 groupings and 120 factors including archives, and 1000 concepts. Archiving retains IDs, evidence, and assessment records.

Open **Method & concepts → Method versions** to **Export method definition** or **Load method JSON**. A method-only export contains definitions and literature, not engineering activities or evidence. A reviewed import previews count changes and affected assessments before application. Missing definitions are archived; changed criteria and linked literature require reapplication; new factor IDs receive blank assessments. A full **Export JSON** remains the backup for earlier workspace snapshots.

See [the method file contract and update examples](docs/ADAPTABLE-METHOD.md). Imports update the current browser workspace. Publication of shared defaults and automatic KNIME synchronization remain future work; updating the repository concept file alone does not change groupings.

## Upload status and deploy-preview troubleshooting

Supporting files remain attached while an activity is Draft. The evidence panel shows attached records separately from current human assessments and provides a direct rubric link. Recording an assessment starts **In review**; **Reviewed** still requires an explicit named review of all current factors. An undecodable image has a fallback and remains downloadable/replaceable.

See [evidence and preview troubleshooting](docs/EVIDENCE-TROUBLESHOOTING.md) for Netlify Drawer compatibility and transferring a workspace between preview hostnames with Export/Restore JSON.

## Prepared A1 case profile

A1 starts with the supplied icon-only button/dropdown-caret case: title, ticket-assignee attribution, documented tool/environment gaps, and a sectioned description. The source text is maintained in `src/data/activityProfiles.js`; contextual readiness checks and comparative workflows are separated from case-specific results. No screenshots or inferred assessment findings are bundled.

Existing browser workspaces keep their saved A1 fields. Open A1 and choose **Load prepared A1 details** to preview the repository text, export a backup, and apply it explicitly. Application changes only the four profile fields, keeps attachments and recorded rationale, and flags recorded assessments for reapplication. A2/A3 and method definitions are unaffected.

## Prepared A2 DevOps operating profile

A2 is fully populated from the specification-to-shipping diagram as a **proposed DevOps operating profile**: accountable roles, a proposed GitHub/CI and isolated validation stack, scope, inputs, agent permissions, human checkpoints, validation requirements, acceptance criteria, and evidence requirements. All four fields have complete text rather than placeholders. These are proposed operating decisions, not claims of an observed successful execution or measured acceleration.

New workspaces use the A2 profile by default. Existing saved A2 records expose **Load prepared A2 details**, with preview, backup and explicit application. The shared prepared-profile loader retains attachments and rationale and flags recorded assessments for reapplication. The wider report/rubric alignment awaits the revised method definitions and human assessment findings.

## Prepared A3 AI-assisted review profile

A3 combines the visible Whetstone review comment with a complete proposed DevOps review procedure. Its four fields identify the review activity, accountable roles, Whetstone/GitHub/Python context, controlled validation requirements, human disposition, acceptance criteria, artifact requirements, and reapplication. The source PR capture is distinguished from this MVP's GitHub PR numbering. The AI tool's medium/security label is source metadata rather than a rubric risk score. No remediation, test success, human approval, or merge is inferred.

New workspaces prefill A3. Existing workspaces use **Load prepared A3 details**, preserving evidence and earlier rationale and flagging recorded assessments for reapplication. All three profiles are now available for review; report-wide criteria/mapping changes and human evidence statuses still require the corresponding reviewed report content. Raw screenshots and code from the source PR are not bundled.
